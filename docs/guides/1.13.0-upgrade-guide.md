# Couchbase Capella Provider 1.13.0: Upgrade and Information Guide

Here is a list of what's new in 1.13.0

## New Features

* Introduce new Organization-Level Roles: Billing Admin, Billing Viewer, and Org Read-Only
* Ability to Select Availability Zones (AZs) on AWS
* Terraform - App Services and App Endpoint Management -Admin users

## Enhancements

* Validate that the database name provider is valid or not, between the length of 2 and 32, during plan time
* datasource to get app service audit log status
* Adds the `couchbase-capella_replication_activation_status` resource
* This change adds two attributes to the `couchbase-capella_replication` resource:

- `mobile_sync_mode`: `off` (default) or `active`
* - Adds `couchbase-capella_cluster_alert_configuration`, managing a cluster's own `configs`, `recipients` and `muted_alerts`
* Customers can now choose the 3 AWS availability zone IDs their **multi-AZ** cluster is deployed in
* Extended acceptance coverage for AZ selection for AWS
* Add alert configuration data sources
* Implement resource for  app service admin user
* Implement app service admin user datasources to list all admins, list with filter, and get 1 admin

## Bug Fixes

* Three acceptance tests fail on every run, masking real regressions in App Service private endpoints and in cluster zones import
* For an AWS cluster whose `disk` block omits `storage` or `iops`, the provider sent `"storage": 0` / `"iops": 0` in the create request instead of rejecting the config
* The V4 update API for an App Service admin user cannot change the password
* `couchbase-capella_app_service_admin_user` with `access_all_endpoints = false` failed on apply with "Provider produced inconsistent result after apply"
* As mentioned in the ticket, the only change needed was to remove the collection field from the queryManage
* Making use of requiredUUIDString() method instead of requiredString() to decline invalid data source immediately, rather than letting it reach the public API
* if provider gets a 201 to create request but cannot unmarshal thre response body, the provider has no way to manage the resource

## Changes

1.13.0 includes new features and general improvements. See the [CHANGELOG](https://github.com/couchbasecloud/terraform-provider-couchbase-capella/blob/master/CHANGELOG.md) for more specific information.

## Breaking Changes

WARNING: **ACTION REQUIRED** - The following changes may require updates to your Terraform configurations:

### Add alerts data source

Adds the `couchbase-capella_alerts` data source. It lists the firing and resolved alerts in an organization using `GET /v4/organizations/{organizationId}/alerts`, with one entry for each alert on each resource. Muted alerts are not included.

**Optional filters**, sent as the endpoint's query parameters and validated at plan time:

| Attribute | Notes |
|---|---|
| `status` | `firing` and/or `resolved`. Both are returned when omitted. |
| `cluster_ids`, `project_ids` | Sets of UUIDs. |
| `severity_levels` | `debug`, `info`, `warning`, `critical`. |
| `from`, `to` | RFC3339 timestamps. Default range is the last 48 hours; `from` can go back at most 31 days. |

**Each entry in `data`:** `alert_id`, `event_id`, `name`, `kind`, `resource_id`, `resource_type`, `resource_name`, `project_id`, `project_name`, `bucket`, `node_hostname`, `severity`, `status`, `starts_at`, `ends_at`, `event_time`. Fields the API omits come back as null. For example, `ends_at` is null while an alert is still firing, and `bucket` and `node_hostname` are only set for bucket and per-node alerts.
